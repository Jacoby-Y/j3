## Stage 1: Children (`<slot/>`)

**Why.** Without children there is no `<Card>`, `<Modal>`, `<Tabs>`, `<Field label>` or page layout component.
`big_ui_test` repeats the same `section { ... } small { ... } .row { ... }` block in Inputs, Widgets, Overlays,
Scroll, Game and more.

**Design.**

```html
<!-- ui/Card.j3ui -->
<script> props { title: string; } </script>
<section class="card">
    <header>{title}<slot name="actions" /></header>
    <slot />                         <!-- default slot -->
    <footer><slot name="footer">Default footer</slot></footer>  <!-- fallback content -->
</section>

<!-- user -->
<Card title="Audio">
    <button slot="actions" on:click={reset()}>Reset</button>
    <label>Volume <input type="range" bind:value={vol} /></label>
    <p slot="footer">Changes apply at once.</p>
</Card>
```

- Slot content is compiled in the **parent's** scope: its expressions, handlers and `bind:` see the parent's
  props, lets and fns, and loop variables of an enclosing `{#each}` in the parent. That's the Svelte rule.
- The parent's `<style>` scopes the slot content. The child's scoped CSS reaches the slot wrapper but not the
  slotted elements, unless the child uses `:slotted(sel)` (add later only if needed).
- `{#if $slots.footer}` is not in the first cut. A child can't ask whether a slot was filled yet.

**Implementation notes.**

- J3 has no closures or traits (`j3c doc lang`), so a slot cannot be a callback value. Use **whole-program static
  dispatch**: the generator already sees every component and every use site (`gen.rs` numbers instances and builds
  the containment graph for cycle checks, around lines 160–260).
  1. Give each use site that passes children a site id. For each child type C, collect the set of
     `(parent type P, site)` pairs.
  2. Generate the slot content as methods on the **parent**: `fn slot_<site>_<name>_update(this: &P, d: &Dom)`
     and `..._paint(this: &P, d: &Dom)`, from the same `upd`/`pnt` emitters, with the parent's name rewriting.
  3. Give the child a hidden `slotSite: int` plus one typed owner field per parent type that uses it
     (`own_P: &P`). The parent sets both right before calling `child.update`.
  4. Where the child has `<slot name>`, emit an `if`-chain over the sites:
     `if this.slotSite == 7 { this.own_Page.slot_7_footer_update(d); } else if ... else { <fallback> }`.
     Do the same in paint.
  5. Check first that a struct field of reference type can stay unset (is null or has a default). If it can't,
     keep one `&Arena`-allocated owner pointer per parent type, or store a `[]` of owners. STOP and ask if J3
     can't express a typed reference that is sometimes unset.
- DOM placement needs no new runtime. Slot content is emitted at the `<slot>` position inside the child's
  `d.enter(...)` / `d.open(...)` stream, so `open` slot numbering stays monotonic. Number slot content in its own
  slot range (for example a `slot` element wrapping it, which `display: contents` behavior would hide). Pick the
  simpler of a real wrapper node or a numbering offset, and write the choice down.
- Stateful things inside slot content (child components, `{#if}` with state, `{#each}`) belong to the **parent's**
  state tables (`this.cN`, `this.ifN`). They're compiled in the parent, so the existing `collect_state` / `number`
  logic applies when it runs over the slot nodes as part of the parent.
- Compile errors: `slot="x"` where the child has no `<slot name="x">`; children passed to a component with no
  `<slot>`; two `<slot />` defaults in one child.
- Remove the "components take no children" line from `j3c doc j3ui` and the 022/06 Gaps.

**Tests.** `ui/tests.rs`: parse and generate for default, named, fallback, slot in `{#each}` (the parent loop var
is used), and nested slots (`Card` inside `Card`). Runtime: a test project whose golden shows a two-level Card, and
a click on a slotted button that changes parent state.

**Done when.** `<Card>` like the example works, and `big_ui_test` has a `ui/kit/Section.j3ui` used by at least
three pages (the full migration is stage 7).

**Done.** `<slot />`, `<slot name="x">fallback</slot>` and `slot="x"` on a direct child work as designed; slot content is compiled
in the owner's scope. `ui/gen.rs`: a pre-pass in `generate` (`declared`, `scan_sites`) checks every component use that passes
children and numbers it as a site; the owner gets `slot<site>_<name>_update/_paint(this, d, i)` methods (`slot_method`, generated
by swapping `G`'s `upd`/`pnt`/`used_*` out, so the normal `seq` emitters run unchanged); the child gets `slotSite`, `slotOwn`,
`slotI` fields (only if it has a `<slot>`) and `slot_elem` emits `d.enter(pos)`, an `if slotSite == N` chain calling the owner, and
the fallback in the `else`. Choices: the owner is stored as an **address** (`this as int`, called back as
`((this.slotOwn as ptr) as &Owner)`), so no typed field per parent type and no unset reference is needed (the plan's STOP case
did not arise); it is re-stored each frame in update and paint, so a `List` that grows cannot leave it stale. The slot is a
`d.enter` construct (no wrapper node, so the DOM is the same as hand-written markup). An enclosing `{#each}` item is re-bound in
the method from the index `slotI` (the list expression is evaluated once more per slot call). `emit` in slot content writes
`this.sev`, merged into the owner's update events. Errors: unknown slot name, children for a component with no `<slot>`, children
with no default slot, duplicate slots, non-literal `name`/`slot`. Tests: `ui/tests.rs` (generation, errors), runtime project
`speculative/14_ui_slots` (`j3c run speculative/14_ui_slots --headless` prints PASS lines: named, fallback, `{#each}` with
index, Card in Card, component in slot content, click on a slotted button, `emit`, slot passed through a second component; also
typechecked by `cargo test --lib ui::`). Idle frames: 3000-frame steady run of that UI: 0 layouts, 0 restyles, 0 arena growth.
`big_ui_test` has `ui/kit/Section.j3ui` (caption prop + default slot) used by `Layout`, `Scroll`, `Widgets` (11 sections).
Slot content state (`{#if}`, child components) lives in the owner, but when the child skips a `<slot>` it rendered last frame, the
owner's `slot<site>_<name>_leave` runs (`destroy()`, then the same resets as entering an `{#if}` branch), so `onDestroy` fires and
the content remounts fresh when the slot returns, as in Svelte. The child keeps two bools per filled `<slot>` (`slotNow<k>` /
`slotWas<k>`) checked at the end of `update`: idle frames cost two compares. Test: `speculative/14_ui_slots` (Modal hiding a
slot, also inside an `{#each}`). Caveats: `<footer>` and `<b>` are not in `ELEMENTS` (the plan's example uses footer);
no `:slotted()`, no `$slots.x`; comps in slot content still obey the "two nested `{#each}`" limit; the LSP does not complete
`<slot>`/`slot=` yet.

## Stage 2: Dynamic styling

**Why.**
- `class` takes plain text only (`gen.rs` `attr`, about line 879), so `ItemSlot` needs
  `class:r1={rarity == 1} ... class:r4={rarity == 4}`.
- There's no way to bind a style value, so `game.Bar` fakes a width by sliding a clipped fill with `left`, and its
  notes say "dynamic width is not an attribute".
- `left` / `top` are one-off attributes (`attrLeft` / `attrTop` in `ui/dom.j3:1030`).

**Design.**
- `class="slot r{rarity} {extra}"`: literal words stay static, and holes produce extra class words. Keep
  `class:name={cond}`.
- `style:width={pct * 100.0}` (a number is px), `style:width="{pct * 100.0}%"`, `style:background={color}`
  (a string goes through the CSS value parser). Inline values beat every rule, and they **transition** like any
  style change, so `transition: width 200ms` on the bar replaces the hand-written easing in `Bar.j3ui`.
- `left={x}` / `top={y}` become aliases for `style:left` / `style:top`. Keep them and point the docs at `style:`.

**Implementation notes.**
- Class holes: generate `d.clsDyn(n, k, text)`, where `k` is the hole index on that node. The runtime keeps the
  last bytes per (node, k) and re-interns only when they change, then marks the node for restyle. That keeps
  idle frames at zero restyles (022 measures `steady`: recomputes 0, and this must stay 0).
- `style:`: add a small inline-override list per node in `dom.j3` (prop id, parsed value), set by
  `d.styleNum(n, prop, v)` / `d.styleStr(n, prop, s)`, which compare to the last value before dirtying. Apply the
  overrides after the cascade in the style resolve step, then hand the resolved value to the existing transition
  code (`cssmotion.j3`) so it retargets from the current value. Resolve the prop name at compile time against
  `cssprop.j3`'s table, with a compile error for unknown props or props the runtime can't set inline (for
  example `animation`, `@font-face` things).
- A string value parses with `cssvalue` at runtime only when the bytes changed.
- Reimplement `attrLeft` / `attrTop` on top of `style:` so panels (`panels.j3:181, 201`) keep working. The panel
  code sets them every drag frame, so keep the no-change fast path.

**Tests.** `css_test` / `dom_test`: class hole churn (same text twice gives no restyle), `style:` override beats a
scoped rule, width transition retargets mid-flight, 10,000 idle frames with 0 restyles. Rewrite `game.Bar` with
`style:width` and a CSS transition, and delete its `tick()` easing. Golden-diff the Game page.

**Done.** `class="a r{n} {x}"` and `style:prop` work as designed (docs: `j3c doc j3ui` "Dynamic style", one line in `j3c doc css`).
`ui/gen.rs`: `attr` splits the `class` text into words; whole literal words stay `clsId`, every word with a `{hole}` is joined
into one `d.clsDyn(n, text)`; `style_attr` emits `d.styleNum(n, k, "prop", f32(expr))` or `d.styleStr(n, k, "prop", text)`
(`k` = the attribute's number on the element, max 8) and checks the name at compile time against `PROP_NAMES` read from the
embedded `ui/css.j3` plus a shorthand list (errors: unknown, `animation`/`transition`/grid tracks/`--vars`, no value, a number for a
shorthand). Runtime: new `ui/dynattr.j3` (`Dyn`: last values by hash+length, parsed declarations, two style ids) and thin glue in
`dom.j3` (`clsDyn`, `styleNum`, `styleStr`, `dynOf`, and `inlineStyle` called from `applyStyle` right after `computeStyle`).
A changed override copies the cascade style into one of the node's two alternating style ids and writes the overrides over it, so
the normal transition code (`motion.onStyle`) retargets from the old id; unchanged values touch nothing (dom_test: 10000 idle
frames, 0 restyles, 0 layouts, no arena growth; also a generated-code run). Text values go through the real CSS parser:
`cssparse.inlineDecl` (declarations copied out, `css.decls` cut back), and `cssmatch.declValue` (factored out of `buildStyle`)
resolves `var()` / `inherit`. Tests: `dom_test.j3` `testDyn`, `ui/tests.rs` (generation, errors); `big_ui_test` `game.Bar` now binds
`width` and its `tick()` easing is gone (fill `transition: width 150ms`, ghost `400ms ease 450ms` for the hold), Game page checked in a
headless screenshot.
Choices and caveats:
- `={expr}` is a **number** (f32, px for lengths); text is `="{expr}%"` or an expression that starts with a quote or backtick. The
  compiler cannot see types, so the plan's `style:background={color}` with a string variable is written `style:background="{color}"`.
- `left={x}` / `top={y}` were **not** re-pointed at `style:left`: their `hasAt` flags also drive the keep-on-screen clamp and the
  `position-try-fallbacks` anchor of popups, and panels set them every drag frame. They keep working as before; docs point at `style:`.
- A numeric value on a property that takes text (color, keyword) panics at runtime on the first frame with a message; a bad text
  value is a warning in `css.warns` and clears the override.
- An override of an inherited property (`style:color`, `font-size`) clears the style cache on each change (children cached under the
  old id would be stale), so animating one every frame costs recomputing the dirty nodes' cascade.
- A gradient given as text allocates paint data each time the text changes. Hot reload (`Dom.restyle`) drops the `Dyn` styles and
  re-parses overrides next update. A dynamic class equal to a static or `class:` one is removed with it when the hole text changes.
- The LSP does not complete `style:`.

## Stage 3: Lifecycle

**Why.** Per-frame logic runs through `class:tick={tick()}` (Overlays, Game, Bar). It reads like a bug, it runs
whenever the attribute is evaluated, and `Bar` works out `dt` from `frameCount()` and assumes 60 Hz.

**Design.** Optional script functions, found by name:

```j3
fn onMount() { ... }            // once, after the first update, before first paint
fn onFrame(dt: f32) { ... }     // every frame before this component's update; dt in seconds from the Dom clock
fn onDestroy() { ... }          // when an {#if} branch or {#each} item drops this instance
```

**Implementation notes.**
- `gen.rs` already emits `init(d)` behind `if !this.ready` in `update` (about line 1614). Call `onMount` there,
  after the first build. Call `onFrame(d.dt())` at the top of `update`.
- Add `Dom.dt()` (seconds since the previous `beginFrame`, clamped to 0.1 s, and honoring `setFrameMs` /
  `J3_FIXED_DT` so goldens stay deterministic).
- `onDestroy`: find where a stateful `{#if}` branch change resets its child state (`Branch { v: -1 }` handling,
  `gen.rs` about lines 1222–1230 and 1509–1560) and where an `{#each}` shrinks (`this.cntN` drops). Call
  `onDestroy` for each instance that is dropped, and reset its state so a re-entered branch remounts (and calls
  `onMount` again). If today's code **keeps** instance state across a branch flip, decide one behavior, document
  it, and test it.
- Validate signatures at compile time (`onFrame` must take exactly `dt: f32`).
- Optionally (cheap): `fn onProps()`, called when a prop changed, if the generator already diffs props. Skip it
  if it doesn't.

**Tests.** Generator tests for signature errors. A runtime test that counts mount/frame/destroy calls through an
`{#if}` toggle and an `{#each}` shrink. Migrate the three `class:tick` uses and delete the pattern from the docs
and examples.

**Done.** `onMount()`, `onFrame(dt: f32)`, `onDestroy()` as designed (docs: `j3c doc j3ui` "Lifecycle"). `ui/gen.rs`: signatures are checked
where script fns are claimed (compile errors; `onFrame` takes one `f32` parameter of any name); `update` calls `this.onFrame(d.dt())`
before the markup and `this.onMount()` at its end on the first call (so children mount first); every component gets a generated
`destroy()` (children, then `onDestroy`, then `ready = false`, so a second call is a no-op). `resets` has a `destroy` mode that
`ifnode` uses to destroy the components of the branch being left before the existing "start fresh on entry" reset, and `each` destroys
the dropped items before truncating its lists. `Dom.dt()` (`ui/dom.j3`): seconds from `dtMs`, 0 on the first frame, capped at 0.1.
Tests: `ui/tests.rs` `lifecycle_fns_have_fixed_signatures`; runtime `speculative/15_ui_lifecycle` (mount/frame/destroy counts through an
`{#if}` toggle holding a component that holds one, an `{#each}` shrink and regrow, idle frames). `big_ui_test` `Game` and `Overlays` use
`onFrame` (`Bar` lost its tick in stage 2); `class:tick` is gone from the examples (it never was in the docs).
Choices and caveats:
- Existing behavior kept: a left `{#if}` branch keeps its stale instance until re-entry replaces it with a fresh one; now it is also destroyed
  on leaving, so entering again remounts. A hidden branch gets no `onFrame`.
- `onMount` runs after the first build, so state it sets shows in the next frame's markup. `onFrame` also runs on that first update.
- Components passed as slot content belong to the owner, so they are destroyed with the owner or its `{#if}`, not when the child that
  renders the slot hides it. The root is never destroyed. `destroy` and `mounting` are now reserved names.
- `onProps` was skipped (the generator does not diff props).

## Stage 4: Lists

**Why.** `{#each}` keeps component and branch state by position (`this.cN.items[i]`, `gen.rs` `each`, about
line 1344), and the DOM reuses children by slot position. Sorting, filtering or removing from a list hands
every later row the wrong instance state, focus, scroll, caret and running transition. Components inside two
nested `{#each}` blocks are also a compile error (`gen.rs:1139`, `:1222`).

**Design.**
- `{#each files as f (f.id)}`: a key expression after the head, which must give an `int` or a `string`.
- Unkeyed loops keep today's behavior (it's fast and fine for static lists).
- Nested `{#each}` with components at any depth.
- Lists of structs are the documented default. `{#each items as it, i}` over `[]Item` already lowers to
  `x[i]` and works, but the docs and examples teach `0..N` over parallel arrays. Fix the teaching in stage 7.

**Implementation notes.**
- Keyed state: per keyed each, keep `keys: List<Key>` from last frame next to the instance lists. Each frame,
  build the new key order and permute the instance lists (`cN.items`, `ifN.items`) to match. Reuse instances
  whose key matches, create new ones, and run `onDestroy` (stage 3) on the leftovers. Keep a reusable scratch
  map in the component's arena so steady frames allocate nothing. Linear search is fine below a few hundred
  items; use a hash map above that and leave a `ponytail:` note naming the ceiling.
- Keyed DOM: add `d.openKeyed(slot, tag, scope, key)` to `dom.j3`. Among the current parent's children it
  finds the node with the same key and moves it into place, so transitions, scroll, focus and `textedit` state
  move with it. `close`/`end` already remove unvisited children. A moved node must not count as removed, so
  `transition:fade` leave ghosts don't fire.
- Nested eachs: the limit comes from state indexing by `self.idx.last()`. Generalise it to a per-level index
  stack, giving state lists of lists or a flattened index with the per-level counts. Keyed and nested together:
  key each level separately.
- Duplicate keys: debug-build warning naming the `.j3ui` line, then fall back to position for the duplicates.

**Tests.** A runtime test: a keyed list of components with per-instance `let` state, reversed, filtered and
inserted into, where the state follows the key. A text input in a keyed row keeps its caret through a sort.
Nested each with components. `steady` with a 1000-row keyed list allocates nothing.

**Done.** `{#each xs as x (key)}` (also `as x, i (key)`, `0..n as i (key)`); nesting with components or `{#if}`s at any depth.
- Generator (`ui/gen.rs`): an `{#each}` that is keyed or holds components/`{#if}` state gets a row struct `<Comp>_R<id>` (state of its body:
  `c<n>`, `if<n>`, nested lists) and a `List<&Row>` in its container (the component, or the enclosing row); the body reads `r<id>`. This
  replaced the `items[idx]` lists and `Branch`, so the two-nested-each errors are gone. Keyed: each frame the key is formatted by a template
  (`` `{expr}` ``) into `Keyed.add`, `finish` matches old rows, then dead rows are `destroy()`ed and the row list is rebuilt in the new order.
  Rows are `make`d per new key, so state and `onMount` follow the key. Unkeyed with state: grow with `make`, shrink with `destroy` (as 3).
  Key type: J3 has no way for the generator to see a type, and template strings are the one expression that formats both int and string,
  so keys are compared as text (`ponytail:` in `ui/keyed.j3`: a typed int fast path needs a checker hook).
- Runtime: `ui/keyed.j3` `Keyed` (two swapped byte buffers: a steady frame compares bytes and allocates nothing; linear matching on a
  changed frame, duplicate-key warning once per list naming `file.j3ui:line`). `dom.j3`: `Node.gk`, `groupNew`/`keyBegin`/`keyEnd` (a row's
  nodes are a contiguous run that `keyBegin` moves to the cursor with `unlinkNode` + `insertBefore`, no `removeNode`, so transitions, focus, scroll
  and text-edit state move with it), `open`/`text` only reuse or remove nodes of the row being built (`ownsNode`), `paintGroup` keeps
  `paintNext` inside the row. Keyed rows use slot `j`, not `i*w+j`, so they are not capped at 4096 rows. This is `keyBegin` on the row rather
  than the plan's `openKeyed(slot, tag, scope, key)`: a row may hold several top-level nodes, text and component roots.
- Tests: `ui/tests.rs` `keyed_and_nested_each`, `each_key_errors`; runtime `speculative/16_ui_lists` (reverse, filter, insert, clear,
  all-new, duplicates, nested keyed and unkeyed lists, optional nodes before/after a row, `{#if}`-gated list left and re-entered, slot
  content inside a keyed row, DOM node identity per key, a 1000-row keyed list idle with no arena growth; run line in `main.j3`). Existing
  `speculative/14`, `15`, `12`, `dom_test`, `layout_test`, `input_test`, `overlay_test`, `motion_test` pass.
Caveats and choices:
- Slot content (a component with children) inside two nested lists is a compile error: the slot method gets one index. One level works, keyed or not.
- Sibling `{#each}` loop variables must have different names in one component (J3 rejects shadowing, as before).
- Dead row ids are reused: a row's `destroy()` calls `Dom.groupFree`, and `beginFrame` moves ids to the free list once no node (a fading
  `transition:fade` ghost included, or a ghost of a row nested in it) can still be taken for the old row's. A list that churns forever
  stops growing `Dom.gpar` (`speculative/16_ui_lists` churn: 10000 frames, nested rows and fade ghosts). Dead rows are pooled too: each
  `{#each}` with rows has a free list `fp<id>` next to `e<id>`; a dead or shrunk-away row is pushed on it and `<Comp>_R<id>.take` pops one
  (`reset(uid)`: components `j3Reset()` in place, `{#if}`s unset, nested lists drained into their own pools) before it calls `make`. The
  churn check asserts the arena grows less than 1 KB over 10000 frames (it was about 8.6 MB). A component's generated reset is
  `j3Reset` (reserved name); `{#if}` branch re-entry still builds components with `new`, so toggling an `{#if}` allocates as before.
- Leave ghosts: `transition:fade` on a keyed row's element fires when the row is removed and not when it only moves (`speculative/16_ui_lists`).
- An unkeyed list holding components keeps rows by position as before; a keyed list with no components is rows of just a uid.
- The duplicate-key warning prints in every build, once per list (no debug-only switch).

## Stage 5: Data flow

**Why.**
- Events carry no data (`emit x` becomes `ev.x = true`), so `ItemSlot`'s `pick` gets its index from the parent's
  loop variable. Inside a reusable component that has its own internal list, that doesn't work.
- Shared state is passed by hand through every level (`demo={demo}` in Hud, Bar, World, Minimap, Controls,
  Inventory, Floaters, ...).

**Design.**
- `events { pick(slot: int); rename(name: string); }`, `emit pick(i)`, and `on:pick={demo.clickSlot(event.slot)}`.
  `event` is in scope in the handler as the payload struct. A plain `events { close; }` stays valid.
- `provide demo;` in a script names a prop or let that every descendant can take with `inject demo: &Demo;`.
  This is resolved at compile time: the generator walks the containment graph and adds a hidden prop along each
  path. Through slots (stage 1), slot content sees the **parent's** provides, not the child's.

**Implementation notes.**
- Payloads: the `emit` token rewrite (`gen.rs` about line 437) becomes `ev.pick = true; ev.pick_slot = <expr>;`.
  `NameEvents` gets the payload fields. In the parent's `on:` handler, emit `let event = PickEvent { slot:

## Stage 10: Styled popups, tooltip, menu keyboard

Historical notes below describe the 2026-10-20 intermediate implementation. Its popup stand-ins and the
DOM/theming/wrapping/type-ahead gaps were superseded by current stage 3; see its Done (3a–3d) notes.
Accessibility gaps remain tracked separately in current stage 13 and plan 024.

**Why.** The select list, color picker and tooltip are drawn with fixed colors (`popup.j3`, `dropdown.j3`,
`colorpick.j3`, `overlays.j3`), so an app's theme stops at the popup edge. Menus built from popovers have no
keyboard navigation.

- Draw the built-in popups as DOM nodes with fixed class names (`.j3-select-list`, `.j3-option`,
  `.j3-option:hover`, `.j3-color-panel`, `.j3-tooltip`), styled by a built-in UA sheet loaded before
  theme.css, so a theme overrides them with normal rules. If moving them into the DOM is too big, read those
  rules' computed values in the current immediate drawing code as the first step.
- Tooltip: `.j3-tooltip` styling, multi-line, `title` delay as a CSS custom property
  (`--j3-tooltip-delay`).
- Menus: in a `popover`, Up/Down move focus between focusable descendants (and elements with a new `menuitem`
  attribute), Right opens a `.sub` child, Left/Escape close one level, Enter clicks. Type-ahead for `select`.
  Add a hover-intent delay for submenus (about 300 ms) so diagonal mouse moves don't close them.

**Tests.** `overlay_test.j3` key paths through a nested menu. Goldens of a themed select and tooltip.

**Done.** (2026-10-20) The smaller first step, not DOM nodes: the select list, color panel and tooltip are still painted by
`dropdown.j3` / `overlays.j3`, but from computed styles of stand-in elements (`.j3-select-list`, `.j3-option`, `.j3-option:hover`,
`.j3-option:disabled`, `.j3-color-panel`, `.j3-tooltip`), so a theme overrides them with ordinary rules. `j3.ui.uastyle` (new) holds the UA sheet
(`UA`, parsed by `uastyle.load` before theme.css: generated roots call it in `new` and in `hot()`; a hand-built `Css` gets it on first use) and
`styleOf` / `lookOf` / `paintBox`. The stand-in sits under the owner's style (the titled element for a tooltip), so `color`, `font-size`,
`accent-color` inherit as before; selectors see only the stand-in chain. Read: background, color, border width and color, radius, padding (tooltip).
Not themable: row height (26), the 8-row limit, the check mark, the scrollbar thumb, the color panel layout; the `:hover` row falls back to the
accent color and a disabled row to faded text when no rule sets them (default look is pixel-identical by construction; checked by eye against
the old screenshots, and goldens of desk-app and idle-breakout pass).
- Tooltip: `\n` in the title makes lines; `--j3-tooltip-delay` on `:root` (a custom property now accepts `ms`/`s`, stored as ms; a bad value warns
  and the earlier one stays). Fade 120 ms unchanged.
- Menu keys (`overlays.menuKeys`, `Dom.setHover`): new bare attribute `menuitem` (focusable, Enter/Space click). In the topmost popover: Down/Up from the
  trigger enter, Up/Down/Home/End wrap over the level's entries (disabled skipped, a `.sub`'s entries are its own level), Right opens an entry's
  `.sub` child (hover is forced to the entry so `.host:hover > .sub` shows it, focus follows once laid out), Left/Escape close one level, Escape on the
  top level closes the popover and focus returns to the opener (existing `ovFocus`). Text boxes, sliders and selects in a menu keep their arrows.
  Hover intent: the outermost submenu host the pointer leaves keeps `:hover` for 300 ms (`HOLD_MS`) unless the pointer enters a sibling host; no
  work on idle frames (it exists only while a hold does). Keys use `setHover(.., false)` (no hold).
- Select type-ahead (`dropdown.typeAhead`, `Dom.ta`): closed (single) or open, ASCII case-insensitive prefix, resets after 1 s, one repeated letter
  cycles; non-ASCII compares bytes exactly. A focused select now turns SDL text input on (`inputs.seeFocus`).
- Tests: `overlay_test.j3` 117 -> 145 (nested menu keys, hold, tooltip delay and parse error, theme override of the UA rules), `input_test.j3` 159 -> 166 (type-ahead;
  the test `opt` helper now gives options a text label). `examples/big_ui_test` Overlays: File menu entries are `menuitem`s with `:focus` styled.
- Not done: real DOM nodes for the popups (a theme cannot add `box-shadow` or children to them), no golden PNG of a themed popup was checked in (verified by
  screenshot in a scratch copy), `.j3-option.selected`, menu type-ahead, roving `aria` roles (stage 12), wrapping long tooltip lines.

## Stage 11: Text stack

Current limits: no per-glyph font fallback, no color emoji, no shaping or bidi (FEATURE_CHECK B).

- **Fallback:** a `font-family` list becomes a real fallback chain. Split runs by `TTF_GlyphIsProvided32` over
  the chain, cache per (code point, chain), and measure and draw per run. This also replaces the "second
  `@font-face` for symbols" workaround in `big_ui_test`.
- **Shaping and bidi:** SDL_ttf ≥ 2.20 built with HarfBuzz shapes runs (`TTF_SetFontScriptName`,
  `TTF_SetFontDirection`). Check the installed version and its HarfBuzz build at startup, and document the
  fallback when it's missing. Bidi needs paragraph-level reordering (UAX #9). Implement the subset that covers
  Arabic/Hebrew mixed with Latin, or STOP and ask if that grows past a few hundred lines.
- **Color emoji:** depends on SDL_ttf / FreeType color bitmap support in the installed version. Probe it. If it's
  unsupported, render emoji from a bundled sprite atlas (Twemoji-style, license checked) keyed by code point.
- Static text selection (FEATURE_CHECK 1) fits here: drag-select across text nodes and Ctrl+C. Make it opt-in
  with `user-select: text`.

**Tests.** Golden pages for mixed-script text, a fallback chain, and emoji. Measure-versus-draw width
consistency tests in `textfit`.

**Done.** (2026-10-20) Steps 1, 2, 3 and 5 landed; step 4 (color emoji) deferred.
- **Fallback chain:** `font-family: "Ui", "Symbols", sans-serif` (the parser now takes a comma list, interned as one comma-joined name). `dom.fontOf` opens each listed `@font-face`
  family at the size; the first is the font and `game.fontFallback(primary, extra)` chains the rest (max 4; names with no face are skipped). `game.textWidth` and `p2Text` split text
  into runs by `TTF_GlyphIsProvided32` (direct-mapped 1024-entry cache by chain + code point; marks, ZWJ, variation selectors stay with the previous glyph) and measure/draw
  each run with its font on one baseline; both use the same run split (`fbRuns`), so layout, carets and drawn glyphs agree. Text the primary draws alone never takes the run path.
  HiDPI: each run goes through `twinFor` for its own font. The chain belongs to the primary's font handle; a `font-family` list opens its own primary handle (`dom.loadFamily`, cached under the whole list and size), so lists with the same first family never share a chain (the twin is per handle in `game`, so the scale is not part of the key; a list costs one `FONT_SRC` slot). Without
  `TTF_GlyphIsProvided32` (SDL_ttf < 2.0.18) `fontFallback` is a no-op. The `big_ui_test` Unicode page has a chain example; its old per-span workaround still works.
- **Shaping:** probe `game.textShaping()` (`TTF_GetHarfBuzzVersion`; installed SDL_ttf 2.22 + HarfBuzz). SDL_ttf shapes nothing complex by default, so each run sets
  script and direction (`game.fontShape`, `TTF_SetFontDirection/ScriptName`) before measuring and drawing: Arabic, Hebrew, Devanagari, Bengali, Thai, Tamil, Telugu.
  Arabic joins (DejaVu 68 px isolated to 49 px). Without HarfBuzz nothing changes (logical, glyph by glyph).
- **Bidi subset** (~150 lines in `game.j3`: `fbRuns`, `fbVisual`): levels at run granularity (first strong letter sets the base; neutrals take the neighbours' direction, digits sit at
  level 2 in RTL context), then UAX #9 L2 reversal of runs for drawing. No embeddings/isolates/mirroring, no `direction`/`unicode-bidi`, at most 64 runs per string (the rest joins the last).
  Reorder is per drawn fragment (per line). Limit: text boxes shape and reorder but caret, selection and hit test use logical order, so they are approximate in RTL text.
- **Color emoji, deferred:** probe on this machine: SDL_ttf 2.22 draws Noto Color Emoji (CBDT) in full color through `TTF_RenderUTF8_Blended`, but at the fixed 109 px strike, ignoring the
  point size, so it blows the line height. Making it work needs a strike-to-size scale in both measure and draw. A sprite atlas fallback was not started: no license-checked
  asset source was available offline and nothing was downloaded. Use a monochrome symbol font in the chain.
- **Static selection:** `user-select: auto | none | text` (inherited; only `text` selects). New `j3.ui.textsel` (run from `inputs.begin`): press on selectable text starts a selection
  (never on a button, input, select or `menuitem`; any other press clears it), drag extends it across text nodes, Ctrl+C copies (blocks joined by a newline), the highlight is
  `accent-color` at alpha 100 (`dom.paintSel`, per fragment, from `Node.sa/sb` marks refreshed each frame only while a selection exists). Password and text boxes are not text nodes,
  so they never take part. Not done: double-click word, Ctrl+A, shift-extend, selecting inside a text box together with page text, bidi-aware hit test.
- Tests: `text_test` 85 -> 88 (chain measure equals the sum of its runs and the layout, duplicates, variation selector, Latin stays on the primary, Arabic shaped and mixed sum),
  `input_test` 166 -> 175 (drag selection across blocks, newline joins, press on non-selectable text and on an input, Ctrl+C when a clipboard exists). Screenshot check of fallback, Arabic,
  Hebrew, mixed and RTL lines (scratch project). Known: Indic shaping not visually verified (no Devanagari font installed); `FONT_SRC` holds 32 fonts, each fallback face at each size
  uses one slot, past it the HiDPI twin is skipped for that font.

## Stage 12: Accessibility

There's nothing today (no roles or names anywhere in `stdlib/j3/ui`). Do it in two steps.

1. **Semantic tree (in J3, testable headless).** Each DOM node gets a role (implicit from the tag: button,
   checkbox, slider, textbox, combobox, dialog, menu, menuitem, list, heading; explicit `role=` attribute), an
   accessible name (text content, `aria-label`, `<label>` association), states (checked, disabled, expanded,
   focused, value/min/max) and actions (click, focus, set value). Emit it from `domhtml` so goldens can diff it.
   Make every interactive element reachable and operable by keyboard (finishes the stage 10 focus model).
2. **Platform bridge (separate plan once step 1 lands).** AccessKit is a Rust crate, which the no-crates rule
   rules out. Linux means AT-SPI over D-Bus through `libdbus` FFI, Windows means UI Automation, macOS means
   NSAccessibility. Start with AT-SPI and test it with Orca. Size it as its own XL plan.

**Tests.** A `domhtml` snapshot of desk-app (stage 7) with roles and names. A keyboard-only walkthrough test that
reaches every control.


**Done (step 1, 2026-10-20).** `j3.ui.a11y` (new): `role` (tag, `<input>` by type, `menuitem`; `role=` overrides), `name` (`aria-label`, an `<img>`'s `alt`,
text content for button/menuitem/option/heading, first heading for a dialog; a control takes its wrapping `<label>`'s text, then `placeholder`, then `title`),
`actions` (`A_FOCUS`/`A_CLICK`/`A_SET`, 0 for disabled, hidden and inert-behind-a-modal), `perform` (focus; click = focus + a synthetic Enter, so it takes the
keyboard path; set a slider or text box, flagged `changed` for the next frame) and `dump` (one line per element with a role: `role "name" checked=.. disabled expanded=..
focused modal inert min/max/now value="..." secret actions=..`, children indented, other text as `text "..."`). Computed only when asked (`domhtml.dumpA11y(d, path)`,
a platform query); no field is written per frame, desk-app `steady` stays 0/0/0. A password box prints `secret`, never its value. `dumpHtml` also writes `role`/`aria-label`.
Markup: new attributes `aria-label`, `role` (stored on `Node` like `title`; `alt` now stores its text as the name) and `tabindex="0"` (focusable like a button, default
role `button`; any other value is a compile error, Tab is always document order). Keyboard audit: Tab/Shift+Tab, Enter/Space on buttons and checkboxes, arrows on sliders
and selects, menu keys and the modal trap were already there; fixed here: `isFocusable` now rejects a node whose *ancestor* is `display: none` or fading out (Tab used to
land inside a closing dialog and in hidden containers), and clickable non-button elements can be reached with `tabindex="0"` (desk-app rows were mouse-only).
desk-app: rows are `role="option" tabindex="0"` in a `role="listbox"` Table, `Field` is a `<label>` (so its slider, checkbox and text box have names), the rename box has
`aria-label`; `tools/golden.sh` diffs `golden/<state>.a11y.txt` for all five states, and `DESK_TEST` has a keyboard walk (Tab cycle equals the number of operable controls,
Enter on a focused row selects it). `stdlib/tests/a11y_test.j3` (40 checks: roles, names, states, hidden, password, actions, Tab walk).
Not done / known: `<label for>` and clicking a label to focus its control (no element ids), `tabindex` other than 0, `aria-selected`/`aria-live`/`aria-describedby`,
a name for a control that merely sits beside a label (wrap it), radio groups (no radio input yet), `visibility: hidden`. Next: `plans/024-a11y-platform-bridge.md`.
